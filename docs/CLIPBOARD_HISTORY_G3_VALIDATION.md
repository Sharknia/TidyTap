# 클립보드 히스토리 G3 검증 기록

- 작성일: 2026-09-23
- 상태: 부분 검증. G3 전체 통과 아님.
- 기준: [작업 계획 G3](CLIPBOARD_HISTORY_WORK_PLAN.md)

## 격리된 클립보드 검사

실제 사용자의 일반 클립보드 대신 `NSPasteboard.withUniqueName()`으로 만든 임시 클립보드에서 다음 동작을 확인했다. `swift test --package-path Packages/TidyTapInputEngine`에 포함된 테스트는 실제 내용이나 TidyTap 권한을 읽지 않는다.

| 검사 | 확인한 결과 |
| --- | --- |
| 텍스트와 RTF | 한 번의 복사를 일반 텍스트와 서식 데이터가 있는 한 항목으로 읽음 |
| 이미지 내용 | PNG·웹 주소·HTML 이미지 표현이 함께 있거나, 대체 텍스트와 단일 이미지 HTML이 있으면 이미지로 읽음. TIFF만 있으면 원본 형식을 유지함. 실제 문장과 RTF 또는 HTML·이미지가 섞인 문서는 텍스트와 지원 서식으로 읽음 |
| Finder 이미지 파일 | 파일 URL 표현이 있으면 텍스트·이미지로 기록하지 않음 |
| 비저장 표식 | `org.nspasteboard.ConcealedType`, `TransientType`, `AutoGeneratedType` 중 하나를 제공한 시험 항목은 기록하지 않음. 표식 없는 일반 텍스트는 계속 기록함. 다른 비밀번호 전체를 판별한다는 뜻은 아님 |
| 수집 시작·종료 | 활성화 이전의 현재 항목을 소급 기록하지 않고, 변경된 항목만 읽으며 중지 후에는 읽지 않음 |
| 항목 크기 초과 | 한도 초과 복사는 기록하지 않고 변경 번호만 로컬 표식에 남긴다. 이후 정상 복사는 계속 수집되며 표식을 지운다. 임시 pasteboard·저장소 테스트로 확인함 |
| 붙여넣기용 쓰기 | 서식 없이 선택하면 일반 텍스트만, 서식 포함이면 RTF·HTML도 기록하며, 이미지는 이미지로 기록함. 붙여넣기용 항목에는 TidyTap 내부 표식과 `AutoGeneratedType`을 붙이고 새 복사 이력으로 읽지 않음 |
| 로컬 저장소 | 정책 수치를 주입한 임시 디렉터리에서 재시작 후 조회, 최신순 정렬, 오래된 항목의 한도 초과·만료 제거, 개별·전체 삭제, 손상 파일 제거, 디렉터리 0700·항목 파일 0600 권한을 확인함 |
| 같은 내용 재복사 | 정확히 같은 텍스트·이미지는 최신 복사 한 건만 남고, 같은 글자라도 서식 데이터가 다르면 구별하는 저장소 테스트 통과. 로컬 실사용 Helper 재시작 후 반복 복사 결과 현재 14개 기록에 동일 내용·서식 중복 그룹 0개를 메타데이터로 확인함 |
| 기능을 끈 상태의 만료 정리 | 격리 설정 앱의 실행 전에 같은 임시 저장소에 만료·미만료 기록을 넣었다. 설정 앱을 열자 만료 기록만 없어지고 미만료 기록은 남는 것을 Release launch smoke에서 확인함 |
| 저장 중 종료 흔적 | 다음 저장소 접근 때 `.pending-*` 임시 파일을 잠금 안에서 정리해 기록 전체 삭제·만료 정책 밖에 민감한 내용이 남지 않음을 확인함 |
| Helper 연결 | 기능이 켜진 동안만 감시·저장을 시작하고 끈 뒤에는 새 복사를 기록하지 않는 경로를 임시 클립보드와 임시 디렉터리에서 확인함. 저장 실패·읽기 거부는 감시를 멈추고 적용 상태를 실패로 보고하는 경로에 연결함 |
| 최초 활성화 사전 확인 | 저장 공간 준비와 명시적 클립보드 읽기 거부 상태를 설정 적용 성공보다 앞에서 검사함. 거부를 주입한 앱 테스트에서 입력 탭을 건드리지 않고 실패로 끝남 |
| 설정 UI의 읽기 거부 | 별도 preferences suite의 실제 설정 앱·Helper를 연결하고 읽기 거부 상태만 주입. 최초 단축키 저장 후 적용 상태 `failed / clipboardHistory.readDenied / enabled=false`, 스위치 off·하위 설정 숨김·거부 안내를 관찰. 실제 TCC 권한 변경은 하지 않음 |
| ‘매번 묻기’ 접근 상태 | 미지정 상태에서 한 번만 접근해 시스템 상태를 확인한다. ‘매번 묻기’가 되면 백그라운드 감시를 시작하지 않고 지속 허용 안내로 종료한다. 허용 상태로 바꾼 뒤 다시 켤 수 있음을 상태 주입 테스트로 확인함 |
| 사용 중 권한 회수 | 새 복사가 없어도 감시 주기마다 읽기 상태를 확인해 중단함. 거부 뒤 허용으로 바뀌어도 사용자가 다시 켜기 전에는 수집을 재개하지 않는 상태 주입 테스트 통과 |
| 창이 열린 동안 새 복사 | 저장 후 내용 없는 변경 신호를 앱에 보내고, 앱은 목록을 새로 읽되 선택한 항목 ID를 유지함. 큰 텍스트의 백그라운드 검색 중 새 복사·선택 보존·삭제 후 다음 선택까지 비표시 창 테스트 통과. 실제 두 프로세스 사이 전달은 미검증 |
| 기록 삭제 UI | 선택 항목 삭제와 확인을 거친 전체 삭제를 로컬 저장소에 연결함. 실제 사용자 흐름과 정책 승인 여부는 미검증 |

현재 변경 검사는 0.25초 간격의 `changeCount` 확인 방식이다. 그 사이 A를 복사한 다음 B가 현재 내용을 대체하면 A를 복원할 수 없다. 임시 클립보드 테스트는 실제 앱의 빠른 복사에서 누락률·CPU 사용량을 측정하지 않는다.

세 비저장 표식은 [NSPasteboard.org의 표식 정의](https://nspasteboard.org/)에 따른 현재 구현 범위다. 이는 앱이 표식을 제공한 경우에만 동작하며, 사용자와 합의된 최종 민감 정보 정책은 아니다.

별도 임시 pasteboard에서 `writeObjects`만 호출하면 내용이 보여도 `changeCount`는 0으로 남았고, `clearContents` 뒤 쓰면 1로 바뀌는 것을 확인했다. [Apple의 `clearContents` 문서](https://developer.apple.com/documentation/appkit/nspasteboard/clearcontents%28%29)는 새 내용을 제공하기 전 이 호출을 첫 단계로 안내하며, [`changeCount` 문서](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)는 소유권 변경 때 값이 증가한다고 설명한다. 따라서 외부 앱이 새 클립보드 소유권을 선언하지 않은 채 내용을 바꾸면 현 감시 방식으로는 그 쓰기를 감지하지 못한다. 일반 앱에서 이 비정상 경로가 얼마나 발생하는지는 확인하지 않았다.

## 일반 클립보드 실사용 시험

2026-09-23에 ad hoc 서명한 격리 Helper를 120초 동안 실행해, 실제 일반 클립보드의 **시험 시작 뒤 새 복사**를 감시했다. 사용자는 평소 작업 중 복사와 스크린샷·Finder 이미지 파일 복사를 허용하고 직접 수행했다. 기존 TidyTap 앱·설정·로그인 항목은 변경하지 않았고, 내용은 로그에 남기지 않았다. 종료 후 Helper와 격리 저장소를 제거했다.

- 텍스트 복사 6건과 PNG 이미지 1건(179,346바이트)이 저장 완료 로그에 나타났다. 실제 백그라운드 복사 감시와 이미지 수집 경로가 동작했다.
- 사용자가 Finder 이미지 파일도 복사했다고 확인했지만 그 뒤 새 저장 로그는 없었다. 파일 제외 동작과 일치하나, 이번 로그에는 복사별 `changeCount`·파일 유형을 남기지 않아 그 한 건의 제외를 직접 입증하지는 못한다.
- Helper의 순간 표본은 시작 시 RSS 11,376 KiB, PNG 기록 후 18,448 KiB, 두 표본 모두 `%CPU=0.0`이었다. 평균 CPU 사용량이나 복사 감지 지연을 의미하지 않는다.
- 두 번째 120초 시험에서는 일반 텍스트와 HTML 표현을 포함한 텍스트 총 11건을 저장했다. 같은 격리 저장소로 Helper를 재시작하자 기존 기록 11건이 다시 읽혔다. 실제 복사의 로컬 저장·Helper 재시작 후 유지는 확인됐다.
- 실제 복사와 창 호출을 함께 실행한 시험에서는 새 텍스트 4건이 기록됐고, 사용자가 `⌥C`로 연 히스토리 창에서 클릭 없이 검색어를 입력해 해당 기록을 찾았다. 격리 앱과 Helper가 같은 저장소를 읽는 경로가 확인됐다.
- 재시작 시험의 `accessBehavior`는 전후 모두 raw value 2였고, 사용 중인 macOS SDK 헤더에서 이는 `.alwaysAllow`다. 거부·재허용 전환은 확인하지 못했다.

생산 코드의 최초 활성화 사전 확인은 `.default`일 때 **기존 클립보드 내용을 한 번 조회할 수 있다**. 조회한 기존 내용은 히스토리에 저장하지 않지만, “기존 클립보드는 읽지 않는다”는 시험 전 안내는 정확하지 않았다. [Apple 문서](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum/default)에 따르면 일반 클립보드의 `.default` 상태에서 프로그램이 읽으면 최초 권한 안내가 발생할 수 있다. 개인정보 안내에는 이 사전 확인 동작을 명시해야 한다.

2026-09-23 로컬 성능 실험에서 무작위 픽셀의 1724×1174 TIFF(약 7 MiB)를 복사 시 PNG로 바꾸는 경로는 211~232ms가 걸렸다. 변환을 없애고 TIFF 원본을 읽는 경로는 0~1ms였다. 같은 Mac·임시 pasteboard에서 각각 세 번 재측정한 값이며 다른 앱과 OS의 지연을 보장하지 않는다. 원본 TIFF를 붙여넣는 대상 앱 호환성은 G2에서 확인해야 한다.

같은 Mac의 별도 임시 저장소에서 난수 5 MiB 항목을 10회 추가하며 저장소의 50 MiB 상한에 접근시켰다. 추가 1~10회는 2~24ms, 마지막 목록 읽기는 20ms였다. 저장 자체의 벽시계 시간이며 이미지 디코딩·실제 앱 복사·UI 반응을 포함하지 않는 단일 측정이다.

30 MiB 난수 데이터를 PNG 유형으로 등록한 임시 pasteboard에서는 읽기 2ms, 10 MiB 항목 상한에 따른 저장 거절 5ms였다. 외부 앱이 데이터를 지연 생성하는 시간과 실제 이미지 디코딩은 포함하지 않으므로, 모든 큰 복사가 입력 탭을 멈추지 않는다는 증거는 아니다.

## 남은 G3 확인

1. 브라우저 이미지·Finder 이미지 파일 제외를 복사별 변경 로그와 함께 재확인하고, 감지 지연·연속 복사 누락률을 계측한다. 텍스트와 클립보드 스크린샷의 실사용 수집은 확인했다.
2. macOS 15.1과 현재 macOS에서 백그라운드 읽기 허용·거부·재허용을 확인한다. 반복 안내를 막는 분기는 구현·주입 테스트했으나 실제 시스템 권한 대화상자와 설정 전환은 아직 검증되지 않았다. Apple은 `.ask`가 프로그램의 일반 클립보드 읽기마다 허용을 묻는 상태라고 설명한다. [Apple `NSPasteboard.AccessBehavior`](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum)
3. 새 복사를 창에서 검색하는 것과 Helper 재시작 뒤 기록 유지는 확인했다. 정식 설정으로 켠 앱·Helper의 저장소 연속 동작은 별도 확인한다.

2026-09-23 당시 코드의 **7일·100개·총 50 MiB·항목당 10 MiB**와 기능을 끈 동안 기존 기록 유지는 확정됐다. 2026-09-28에는 같은 내용의 재복사와 성공 응답을 받은 히스토리 붙여넣기 요청도 기존 한 항목의 최근 시각을 갱신하도록 추가됐다. Helper의 성공 응답은 붙여넣기 키 이벤트 전송 확인이며 대상 앱의 실제 삽입 확인은 아니다. 수치 확정은 만료·초과 처리의 실제 사용자 경험이나 전체 수용 기준 통과를 의미하지 않는다.

따라서 현 단계에서 G3 수용 기준 AC-03·10·18·21을 완료로 표시하지 않는다.
