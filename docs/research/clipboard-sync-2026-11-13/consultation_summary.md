# 아스트라 협의의 결론 변화와 확인 근거

이 문서는 사용자에게 제안할 결론과 검증 근거를 기록한다. 기존 제품 결정이나 실제 시험 결과로 저장하지 않는다.

| 순서 | 아스트라 제안 | 대조·반례 | 협의 결과 |
| --- | --- | --- | --- |
| 독립 초안 | CKSyncEngine·영구 UUID·삭제 우선·본문 없는 삭제 표식 | 만료까지 영구 표식이면 데이터가 계속 늘어남. 1,000개/일 가정은 연 365,000개 | 모든 만료의 영구 표식 권고 철회 |
| 삭제 직접 제어 비교 | 서버 버전이 있는 변경은 조건부 갱신·unknownItem 중단, 결과 불명 첫 생성은 보류 | 최초 미도달과 생성 성공 후 삭제는 서버 부재 조회만으로 구분 안 됨. 샘플의 재업로드는 앱 정책 | 자동 복구 포기와 부활 방지의 경계·별도 증거 필요 확인 |
| 생성 수신증 대안 | 설치별 연속 순번과 항목 생성을 같은 서버 원자 배치에 저장 | 순번/복원/실패/중단·정리까지 별도 프로토콜. ACK 불명 보수안은 내부 재시도 제어를 전제 | 수신증은 v1 최소안 아님. 보수안 보장도 공개 계약 대조 필요 |
| 공개 SDK 재시도 검증 | 앱의 다음 배치 공급에서 모호한 ID를 거절 | 모든 실제 네트워크 재시도가 delegate를 다시 통과한다는 공개 보장은 찾지 못함 | ‘부활 방지 보장’ 철회. 앱이 공급하는 새 배치 차단까지만 입증 |
| 관리형 대안 재평가 | 기존 파일 유지의 비용을 낮게, 직접 복구 책임을 작게 봤다는 점 재검토 | 새 기능은 어느 방식이든 모델·이관·정책 필요. Core Data는 저장과 변경 이력을 함께 관리 | 두 Mac에서 관리형 개인 DB 삭제를 먼저 검증하는 방향으로 최종 권고 변경 |

실제 기존 동작은 독립 초안 후 제공했다. 파일 저장, 붙여넣기 시도 시작의 최근 시각 갱신, 그 시각 기준 7일, 본문+서식 중복 최신 1건, 1,000개/50MiB/항목10MiB다. 이를 변경하는 제안을 기존 사용자 결정으로 취급하지 않았다.

아스트라 최종 권고는 관리형 후보의 우선 검증이다. OFF의 비공개 의미·중복·앱/Helper 소비·만료/한도·이관은 앱 책임으로 남는다. 실제 두 Mac 시험을 하지 않았으며, 프레임워크를 사용하면 모든 경합이 자동 해결된다고 합의하지 않았다.

주 에이전트는 Apple 문서·샘플 코드·실제 .clip 저장 코드와 현재 설치 SDK 헤더를 별도로 대조했다. 샘플의 unknownItem 재업로드와 내부 재시도 공개 보장 부재를 확인했고, Core Data의 영속 이력/미러링·유일성 제약·소비 후 이력 정리·private/public 삭제 차이를 확인했다. 코드나 계정/클라우드는 변경하지 않았다.

첫 프롬프트 외에 후속으로 검토한 질문은 영구 표식 누적, 첫 생성 ACK 불명, fetch-before-send 보장, OFF 중 신규 기록 정책, Core Data 비용 비교, 내부 재시도 검사 보장, 기존 파일 구조에 대한 앵커링 가능성이었다. 후속 질문은 기존 계획/리뷰를 읽지 못하도록 계속 제한했다.
