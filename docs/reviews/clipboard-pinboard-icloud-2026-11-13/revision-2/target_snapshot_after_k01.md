# 고정 보관함·전체 히스토리 iCloud 동기화 개발 계획

- 작성일: 2026-11-13
- 개정: 0.2, 2026-11-13 금붕어 리뷰 G01~G07 반영
- 기준 코드: `main`의 `8d1f219`
- 상태: 개발 계획. 제품 코드·Apple 계정·클라우드 설정은 변경하지 않았으며 구현·배포 완료를 뜻하지 않는다.
- 사용자 확정 범위: 보관함 1개, 보관함의 고정 항목과 일반 히스토리를 함께 iCloud로 동기화.
- 근거: 이번 대화의 사용자 확인, [기존 URS](CLIPBOARD_HISTORY_URS.md), 현재 저장소·앱·Helper 코드. 이전의 ‘고정 항목만 동기화’ 권고는 이번 범위에 적용하지 않는다.

## 1. 목표와 범위

텍스트·이미지를 하나의 보관함에 고정하고, 일반 히스토리까지 같은 Apple 계정의 다른 Mac에서 검색·붙여넣기할 수 있게 한다. 보관함 1개는 항목 1개 제한을 뜻하지 않는다.

이번 계획은 기존 macOS 앱의 Mac 간 동기화를 대상으로 한다. iPhone·iPad 앱·키보드, 여러 보관함, 보관함 공유, 항목 편집, OCR은 포함하지 않는다. 기존의 텍스트·서식·이미지 지원 범위와 단축키·미리보기·붙여넣기 경로를 재사용한다. 파일·폴더 지원은 추가하지 않는다.

| 항목 | 상태 | 내용 |
| --- | --- | --- |
| 고정 보관함 | 사용자 확정 | 보관함 1개에 여러 텍스트·이미지를 고정 |
| 동기화할 데이터 | 사용자 확정 | 고정 항목과 일반 히스토리 모두 포함 |
| 기기·계정 | 계획 범위 | 같은 Apple 계정의 Mac 간 사용. 다른 사람과 공유하지 않음 |
| 저장·동기화 방식 | 기술 권고 | 로컬 저장을 유지하고 CloudKit 개인 데이터베이스와 동기화 |
| 보관·삭제·초기 업로드 정책 | 아래 제안 | 구현 전에 세부 동작 확정. 사용자 확정 요구와 구분 |

## 2. 사용자 흐름

1. 기존 호출 단축키로 히스토리를 연다. 일반 히스토리와 고정 보관함을 전환할 수 있고, 기존 전체/이미지 필터와 텍스트 검색을 각 목록에 적용한다.
2. 선택 항목을 고정하면 보관함에 나타난다. 일반 히스토리에 있던 항목은 그 목록에도 유지하는 안을 제안한다. 고정·해제 조작만으로 시스템 클립보드를 바꾸지 않는다.
3. 보관함에서도 방향키·미리보기·Enter·더블클릭·서식 선택을 기존과 같이 사용한다. 고정 항목은 일반 기록의 만료·개수·총용량 정리로 자동 삭제하지 않는다. 고정 목록에서는 ‘고정 해제’만 제공하고 별도의 ‘모든 목록에서 삭제’ 명령은 추가하지 않는 기준안을 제안한다. 일반 기록의 삭제 버튼과 구분한다.
4. 설정에서 iCloud 동기화를 켠다. 일반 히스토리와 고정 항목, 현재 보관 중인 기존 기록도 업로드되는지 안내한다. 기본 꺼짐과 기존 기록 포함 업로드를 제안한다.
5. 다른 Mac에서도 같은 계정으로 동기화를 켜면 양쪽 기록과 고정 상태가 합쳐진다. 네트워크가 없어도 로컬 검색·고정·붙여넣기는 가능하고, 변경은 재연결 후 반영한다.
6. 동기화 꺼짐·진행 중·대기·오류 상태와 재시도 경로를 제공한다. 완료되지 않은 항목을 동기화 완료로 표시하지 않는다. 즉시 전파나 고정된 완료 시간을 약속하지 않는다.

원격 항목 도착은 시스템 클립보드 쓰기나 새 로컬 복사로 처리하지 않는다. 열린 패널의 선택·검색·입력 초점도 빼앗지 않는다.

아래는 구현 기준으로 권하는 안이다. 이번 대화에서 사용자가 확정한 것은 1절의 기능 범위이며, 이 표의 세부 정책까지 확정한 것은 아니다.

보관함 표시 순서, 고정 저장 한도, 계정 전환 시 이전 계정 로컬 기록의 표시·보존 방식은 미정이다. 보관 기간 선택 UI나 기기별 사용자 설정은 이번 범위에 추가하지 않는다. 일반 기록의 7일은 최근 복사·히스토리 붙여넣기 시도 기준이며, 원격 다운로드 시점으로 연장하지 않는다. 성공 응답 기준으로 변경하지 않는다. 현행 근거는 [피드백 변경 기록](CLIPBOARD_PASTE_FEEDBACK_VALIDATION.md)과 `Sources/App/AppDelegate.swift`의 `paste(_:style:)`다.

기간 만료·공통 한도 정리는 일반 히스토리의 논리적 제거와 고정 콘텐츠 보존을 구분한다. 오프라인·앱 종료 중 모든 기기의 파일이나 원격 데이터가 즉시 물리 삭제된다고 안내하지 않는다. 정리 전 최신 원격 변경과 고정 상태를 병합하고, 기기 시계 차이가 오래된 변경을 최신으로 취급하지 않게 한다.

## 4. 구현 구조

### 로컬 저장과 변경 이력

- 현재 `ClipboardHistoryStore`는 파일별 UUID·시각·본문을 저장하고, 앱과 Helper가 같은 디렉터리 잠금을 사용한다. 복사마다 UUID를 만들며 `prune()`가 만료·중복·용량에 따라 파일을 삭제한다. 이 경로에 고정 표시만 붙이지 않는다.
- 일반 히스토리 포함 여부와 고정 여부를 독립적으로 저장한다. 일반 기록에서 제거되더라도 고정 데이터는 유지되어야 한다. 데이터가 겹치면 저장 구조를 불필요하게 이중화하지 않는다.
- 전 기기에서 같은 항목을 식별할 ID, 동일 내용·서식 판단, 복사·사용·고정 변경 시점과 삭제 상태를 정의한다. 재복사·여러 기기의 같은 내용·포맷이 다른 내용은 각각 검증한다. 전송 재시도나 원격 재수신으로 ID를 다시 만들지 않는다.
- 본문과 변경 대기열을 일관되게 저장한다. 로컬 저장 완료 후 앱이 종료돼도 미전송 변경을 잃지 않아야 한다. 단순 알림만 전송 예약의 근거로 삼지 않는다.
- 삭제·해제와 오래된 오프라인 변경의 순서를 판별할 정보를 둔다. 삭제된 내용을 오래된 기기가 재업로드해 되살리지 않게 하고, 사용자가 이후 명시적으로 다시 복사·고정한 새 동작은 구분한다. 전체 삭제와 오프라인에서 새로 복사한 기록의 경계도 정의한다.
- 이전 형식은 백업 후 이관한다. 최초 이관과 재시도가 같은 데이터를 중복 생성하지 않게 하고, 도중 실패 시 기존 데이터를 읽을 수 있어야 한다. 동기화 실패를 이유로 기존 파일을 지우지 않는다.

### 저장소 버전 전환과 되돌리기

다음은 이번 계획의 기술 기준이다. 저장 포맷·ID·병합 규칙 자체는 1단계 설계 산출물에서 확정하며, 아래 버전 경계는 그 선택과 관계없이 지킨다.

1. 기존 `clipboard-history`에는 새 형식을 쓰지 않는다. 새 데이터는 같은 Application Support 영역의 형제 디렉터리 `clipboard-library-v2`에만 쓴다. 새 포맷을 옛 `.clip` 디코더가 읽거나 정리하지 못하게 한다. 계정별 하위 경로·계정 없는 로컬 영역은 1단계에서 정한다.
2. 전환 전 기존 앱·Helper writer를 정지하고 프로세스 식별·종료·잠금 해제를 확인한다. 기존 `HelperLauncher`의 프로세스 신원 검사·종료 경로와 `prepareForUpdate`를 재사용하되, 현재 IPC가 writer 정지를 보장한다고 가정하지 않는다. 종료 확인이 실패하면 이관을 시작하지 않는다. 복사 수집 중단·재개도 시험한다.
3. 정지 상태에서 기존 저장소의 파일 목록·개수·검증용 체크섬과 권한을 보존한 백업을 만든다. 내용은 출력하지 않는다. 별도 staging 영역에 새 형식을 작성하고 항목 수·지원 콘텐츠·원래 보관 시각을 검증한 뒤 완료 표시와 디렉터리 전환을 기록한다. 이관 트랜잭션 중 원본 백업은 삭제하지 않는다. 이관 백업의 보존 기간·검증 후 정리 조건·사용자 안내는 1단계 설계에서 정하며, 일반 기록의 보관 기간이 백업의 즉시 물리 삭제까지 보장한다고 안내하지 않는다.
4. 새 writer는 완료 표시가 있는 v2 저장소만 연다. 그 전에는 실패/대기 상태로 남고 부분 이관 결과를 수집·동기화하지 않는다. 강제 종료 후 staging은 확정 데이터와 구분해 검증·재시도하고 원본을 다시 가져와 중복 생성하지 않는다. 완료 표시와 전환의 정확한 원자성 계약은 1단계에 기록한다.
5. 전환 실패는 기존 형식과 설정을 보존한 상태로 복구한다. v2를 옛 형식으로 자동 역변환하지 않는다. 이전 앱으로 다운그레이드하면 이전 스냅샷과 그 뒤 구버전에서 새로 모은 로컬 기록만 보인다. v2의 새 기록·고정·원격 데이터가 구버전에 보인다고 약속하지 않는다.
6. 다시 새 버전으로 올라오면 기존 v2를 먼저 보존하고 이미 반입한 옛 스냅샷을 재업로드하지 않는다. 다운그레이드 기간의 신규 로컬 복사는 최초 반입 기록과 구분한다. 삭제 뒤 옛 스냅샷을 재반입해 되살리지 않는 식별·반입 ledger는 1단계 설계와 사건표 E08로 검증한다. 안전하게 구분할 수 없으면 자동 재반입을 중단하고 v2를 유지한 채 안내한다.

이는 구버전이 동시에 실행돼도 괜찮다는 약속이 아니다. v2 데이터 격리는 마지막 보호선이며 동시 writer를 허용하는 설계가 아니다. 실제 업데이트·다운그레이드 시험 전에는 이관 안전성을 완료로 표시하지 않는다.

### CloudKit와 프로세스 수명

- CloudKit 개인 데이터베이스와 `CKSyncEngine`을 우선 검증한다. 텍스트·서식·이미지 전송과 제한 처리를 확인하고 이미지 등 큰 본문은 CloudKit asset 사용을 검토한다. 새 외부 서버·계정 서비스·패키지는 추가하지 않는다.
- 동기화 엔진은 한 프로세스만 소유한다. 기존 앱·Helper 양쪽의 복사·사용·삭제·고정 변경은 공통 저장 계층을 거친다.
- 0단계에서 엔진을 실행할 프로세스를 확정한다. 현재 Helper는 앱 안의 독립 실행 파일이므로 CloudKit 권한이 필요한 실행 주체의 번들·프로비저닝 조건을 확인해야 한다. Helper에 entitlement만 추가하면 된다고 가정하지 않는다. 주앱 소유 방식은 설정 창·임시 패널 종료 후 수명과 비활성 실행을 함께 검증한다.
- 기존 ‘설정 창 닫기·앱 종료 뒤에도 켜진 기능 유지’ 흐름과 로그인·업데이트의 프로세스 교체를 확인한다. 기능 끄기와 동기화 끄기는 수집·송수신 중 무엇을 멈추는지 구분한다.
- 동기화 상태를 디스크에 저장하고 계정별로 격리한다. 일시적 네트워크 오류·서비스 제한과 로그인·권한·용량 문제를 구분해 안내한다. 원격 수신을 다시 업로드하는 순환을 막는다.

현재 `.clip` 디렉터리를 iCloud Drive로 옮기는 방안은 채택하지 않는다. 현재의 로컬 파일 잠금만으로 기기 간 변경 순서·삭제·다운로드·충돌 처리가 해결되지 않는다.

### 기존 진단 로그 처리

현재 `TidyTapClipboardPasteLog`는 검색어·선택 텍스트 미리보기를 기록한다. 위 비기록 요구를 만족하려면 저장소만 계정별로 나누는 것으로는 부족하다.

- 1단계에서 `AppDelegate.logPendingClipboardSelection`의 검색어·본문 미리보기와 내용에서 계산한 hash를 기록하지 않도록 바꾼다. 진단은 임의 시도 ID·결과 코드·콘텐츠 유형·크기·경과 시간으로 제한한다. `TidyTapProduct.swift`의 로그 설명과 관련 시험도 같은 기준으로 맞춘다.
- 새 버전 writer 정지/전환 절차에서 기존 paste 로그를 `TidyTapClipboardPasteLog.clear()` 경로로 정리한다. 운영 로그를 백업·CloudKit 업로드·구형 기록 이관 대상에 넣지 않는다. 삭제 실패 시 성공으로 표시하지 않고 로컬 오류·재시도 상태로 둔다. 이 정리가 확인되기 전에는 동기화 활성화 완료를 표시하지 않는다.
- 계정 전환·일반 기록 전체 삭제 시에도 로그 정리 경로가 실패를 숨기지 않는지 확인한다. 일반 기록/고정 보존 정책과 로그 정리는 별개이며 로그 정리를 이유로 보관 데이터를 지우지 않는다.
- 합성 원문 표식을 검색어·선택 텍스트에 넣고 정상·실패 시도를 실행한 후 로그에 원문·내용 hash가 없는지 시험한다. 권한 없는 실제 사용자 로그를 열거나 본문을 출력하지 않는다. 시험 fixture는 합성 데이터만 사용한다.

### CloudKit 시험 연결의 격리

현재 `TidyTapLaunchSmoke`의 설정 suite와 `TidyTapIPC`의 알림 object는 로컬 경계만 분리한다. CloudKit 컨테이너·환경·개인 DB·계정·zone을 격리하는 기존 기능은 없다. 이름 있는 pasteboard·임시 저장소·합성 데이터만 사용해도 실제 CloudKit 연결이 안전해지는 것은 아니다.

- XCTest와 일반 `launch-smoke`/clipboard gate는 실제 CloudKit 클라이언트 생성·구독·송수신을 금지한다. 동기화 활성화 설정을 시험할 때도 제어 가능한 가짜 전송을 주입한다. 주입이나 시험 설정이 빠지면 실제 연결로 대체하지 않고 오류로 끝낸다. 잘못된 suite 등으로 `TidyTapLaunchSmoke.current()`가 nil을 반환하더라도, 시험 실행 표식이 있으면 운영 모드로 되돌아가 실제 연결하는 경로를 금지한다.
- `TidyTapLaunchSmoke.swift`와 앱의 동기화 생성 경로·scheme·시험 스크립트에 이 차단을 연결한다. 실제 연결 생성 횟수와 송수신 요청 0건을 자동 시험으로 확인한다. 시험용 임의 플래그 하나만으로 운영 설정을 재사용하지 않는다.
- 실제 Gate0/수용 송수신은 별도 명시적 실행으로 분리한다. 네트워크를 켜기 전에 Gate0 문서에 실행 후보·서명/entitlements, 사용할 container ID·환경·private DB·시험 zone, 시험 계정 별칭과 합성 데이터 범위를 기록하고 검사한다. 빠진 값·서명 환경 불일치·허용 영역 밖 요청은 실패로 처리하며 기본/운영 영역으로 대체하지 않는다. 계정 로그인 정보·토큰·실제 이메일은 문서·로그에 기록하지 않는다.
- 실제 프로브는 일상 사용 계정과 분리한 시험 Apple 계정과 전용 시험 컨테이너를 기본으로 한다. 로컬 복사 수집은 끄고 합성 fixture만 넣으며, 자동 XCTest/smoke와 같은 실행으로 실제 송수신을 켜지 않는다. 시험 영역 밖의 읽기·삭제 요청과 운영 기록 반입이 없음을 확인한다.
- 최종 배포 후보는 실제 Production 환경·최종 컨테이너 설정도 확인해야 한다. 이때도 시험 Apple 계정의 분리된 private DB와 명시한 시험 zone·합성 데이터만 사용한다. 개발 환경/다른 시험 컨테이너에서의 성공을 최종 후보 수용으로 대체하지 않는다. 시험 계정·필수 두 Mac·안전한 연결 영역을 확보하지 못하면 실제 시험을 미실행으로 남기며 운영 사용자 데이터로 대체하지 않는다.
- Gate0/1 산출물에 연결 허용/차단 조건과 전송 대역 주입 지점을 반드시 넣는다. 시험 데이터 정리는 허용된 시험 namespace에 한정하고, 실제 사용자 기록·운영 zone을 읽거나 정리하는 시험을 만들지 않는다.

| E11 시험 연결 차단 | 자동 시험/smoke에서 sync-on, 가짜 전송 누락, 잘못된 suite, 실제 시험 설정 누락·불일치·영역 밖 요청을 각각 주입 | 자동 시험은 실제 CloudKit 클라이언트/구독/송수신 0건. 설정 오류는 운영 모드/기본 컨테이너로 대체하지 않고 실패. 실제 시험은 검사한 허용 영역의 합성 항목만 송수신·정리 | AC-S15 |

같은 내용의 동시 복사, 서로 관찰하지 못한 동시 고정/해제, 시계가 다른 두 기기의 만료·한도 정리처럼 현재 규칙만으로 결과가 하나로 정해지지 않는 경우는 1단계 설계 산출물의 필수 사건표다. 각 행에 이벤트 순서/동시성·선택한 충돌 규칙·최종 일반/고정 수·삭제 상태·보관 시각을 기입해야 3단계 시험 구현으로 넘어갈 수 있다. E06~07의 남은 결과도 그 산출물 없이 구현자가 임의로 정하지 않는다.

실기기 송수신 시험은 시작/재연결/수동 재시도 시각, 로컬 저장 성공, 전송 확인, 원격 수신·반영, 잔여 변경과 오류 코드를 기록한다. 관찰을 끝내도 미해소면 원인을 기록하고 해당 AC는 부분/미실행으로 둔다. 무한 대기하거나 ‘영구 대기 없음’이라고 판정하지 않는다. 자동 시험은 합성 시계·지연/순서가 제어되는 전송 대역으로 재현한다.

## 8. 현재 검토 사항

현재 고정·동기화 기능의 실제 사용자 데이터는 없다. 아래 등급은 현재 구현 전 상태를 기준으로 하며, 이미 데이터 손상이 발생했다는 보고가 아니다.

| 등급 | 항목 | 조치 시점 |

| 중간·미확인 | TidyTap App ID·CloudKit 컨테이너·프로비저닝 및 실행 주체의 실제 연결 가능성 | 0단계에서 확인. 불가능한 조건이 확인되면 구체적인 차단 사유로 재분류 |
| 중간 | 일반 기록 자동 정리·중복 제거를 그대로 쓰면 고정 상태를 보호하지 못함 | 1단계 전에 모델·정리 정책 확정 |

## 9. 기술 근거

- [Apple Developer ID 안내](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/): Developer ID 앱의 CloudKit 사용과 provisioning profile 검증 안내.
- [CloudKit 활성화](https://developer.apple.com/documentation/cloudkit/enabling-cloudkit-in-your-app): 컨테이너·capability 설정.
- [CKSyncEngine](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5): 동기화 일정은 시스템 상태에 따라 달라지며, 상태 저장·충돌·계정 변경 처리는 앱 책임. CloudKit·원격 알림 권한 필요.
- [TN3125 프로비저닝](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles): 제한된 권한을 쓰는 실행 파일의 프로파일과 번들 조건.

이 문서는 계획 작성 시 확인한 근거를 담는다. Apple 계정 자원 생성·프로덕션 스키마 반영·실제 송수신·공개 릴리스는 수행하지 않았다.
