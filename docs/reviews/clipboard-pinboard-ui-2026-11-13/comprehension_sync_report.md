## What this proposes

주인님, 최근 기록과 보관함을 같은 패널의 두 탭으로 나누고, 창을 열 때마다 최근 기록부터 보여주는 계획입니다. 같은 표시 세션 안에서는 탭별 검색·필터·선택·스크롤을 보존하고, 마우스와 창 내부 ⌘1/⌘2로 전환합니다. 고정·해제·일반 기록 삭제는 저장 성공 뒤 반영하며, iCloud 설정은 상위 저장·동기화 계약이 준비된 뒤 연결합니다.

## How the existing system works, per this document

문서상 기존 패널은 왼쪽 목록과 오른쪽 미리보기, 검색과 전체/이미지 필터, 기존 붙여넣기·취소 키 처리를 갖고 있습니다. 현재 항목 모델에는 고정 상태와 일반 기록 소속이 없으므로 실제 보관 기능은 상위 Gate1 저장 계층에 의존합니다. 이번 문서는 제품 구현 전 계획이며, 저장 스키마·충돌 병합·실제 동기화 안전성은 아직 확정하거나 검증한 것으로 취급하지 않습니다.

## C01 / Major / 중간: 재열기와 단일 변경 제한

- 검토 시점 74·100·102·153행. 요청 중 한 건만 진행한다고 하지만 닫고 다시 열었을 때 새 요청을 허용하는지 모호했다.
- 반영: 제한은 현재 표시 세션의 고정/해제/삭제 UI 조작이며 재열기 후 새 요청을 허용한다고 명시했다. 계정별 저장 API는 이미 접수한 작업을 포함해 접수 순서로 직렬 반영하는 U0 계약을 추가했다. 이전 UI 완료와 최신 저장 알림을 구분하고 표시 시점의 계정 핸들에 저장 작업을 묶는다.
- 검증 연결: UI-T09의 닫기/재열기/새 요청/늦은 완료.

## C02 / Major / 중간: 첫 snapshot 거부의 결과

- 검토 시점 90·100·120·157행. 유지할 유효 목록이 없는 첫 입력 실패의 화면을 구분할 수 없었다.
- 반영: show는 이전 표시 데이터를 폐기하고 첫 입력 검증 실패 시 false를 반환하며 패널을 열지 않는다. 선택·콜백·키 상태를 비우고 AppDelegate가 기존 열기 오류 경로를 사용한다. 이미 열린 같은 세션의 잘못된 갱신만 현재 유효 목록을 유지한다.
- 검증 연결: UI-T13의 최초 거부/표시 중 거부/계정 전환.

위 문서 보완은 검토 완료 응답 뒤 주 에이전트가 적용했다. 이해도 재검토 상한 1회를 사용했으므로 이 단계에서 추가 반복하지 않는다. 수정본은 뒤의 설계·구조·전체 재검토·구현 준비도에서 읽으며, 같은 이해도 검토자가 수정 후 통과 판정을 했다고 주장하지 않는다.

해당없음: Gate0/1, 주기·병합 정책 미정, 실제 한글 입력·붙여넣기 검증은 계획에 명시돼 새 누락으로 세지 않았다. 검토자 ui06_comprehension_sync는 persona·대상 1~178행만 전문 읽었고 코드·상위 문서·외부자료·다른 보고서·메모리·시험·수정은 하지 않았다고 보고했다. 수정 전 대상은 target_snapshot_with_sync_options.md에 보존했다.
