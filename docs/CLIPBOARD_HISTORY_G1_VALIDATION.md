# 클립보드 히스토리 G1 검증 기록

- 작성일: 2026-09-23
- 상태: 진행 중. G1 전체 통과 아님.
- 기준: [작업 계획 G1](CLIPBOARD_HISTORY_WORK_PLAN.md)
- 환경: macOS 26.5.2, Xcode 26.6, 최신 실사용 시험은 ad hoc 서명한 격리 Debug 빌드

## 실험 격리

`TIDYTAP_CLIPBOARD_G1_PROBE=1`에서만 실행되는 앱/Helper 시험 경로를 추가했다. Helper는 시스템 클립보드의 기존 내용을 읽지 않고, 미리 준비한 일회용 기록만 붙여넣는다. Helper 잠금은 `TIDYTAP_LAUNCH_SMOKE_PREFERENCES_SUITE`의 테스트 전용 영역을 사용했다. 설치된 TidyTap 앱·설정·로그인 항목을 교체하지 않았다. 시험 앱 번들은 `/tmp/tidytap-clipboard-gates.*/DerivedData/Build/Products/Debug/TidyTap.app`에 생성했다.

자동 실행으로 시험 창이 뜻밖에 초점을 가져갈 수 있음을 확인해, 해당 자동 실행 경로는 제거했다. 현재 시험 창은 사용자가 호출 키를 눌렀을 때만 열리도록 했다. 임시 앱과 Helper는 확인 시점마다 정확한 테스트 프로세스를 식별해 종료했다.

## 남은 G1 확인

1. 설정 앱이 이미 실행 중일 때, `⌘Q`로 종료된 뒤, 로그인 Helper 시작 후의 세 경로를 분리해 확인한다. 격리 설정 UI에서 실제 Helper 적용은 확인했지만 정식 설치와 로그인 등록 전체는 아직 재현하지 않았다.
2. 두 모니터와 전체 화면에서 창 위치와 자동 검색 초점을 확인한다.

Developer ID 서명 시 로컬 키체인이 `errSecInternalComponent`를 반환했다. 설치 앱·권한을 변경하지 않고 최신 Debug 앱/Helper를 ad hoc 서명해 격리 시험을 진행했다. 배포 서명 문제는 해결되지 않았다.

격리 Helper는 키 수신·이벤트 전송·AX 접근 권한이 모두 참이었다. 시험 기록은 일회용 `TidyTap G2 test text` 하나였다. 실제 `⌥C` 입력으로 창을 열었고, 두 번의 의도적 Enter 시험에서 TextEdit에 문구가 각각 한 번 입력됐다고 사용자가 확인했다. 앱 프로세스에는 AX 권한이 없어 붙여넣기를 Helper로 옮겼다.

재호출 시험에서는 Esc 뒤 원래 앱을 다시 활성화하지 않아 마우스 클릭 전까지 호출이 실패했다. 이를 고친 다음에도 macOS가 시험 앱 대신 설치된 같은 번들 ID의 설정 앱을 열었다. `/tmp`의 심볼릭 링크 경로를 해소해 실행 중인 시험 앱을 정확히 찾고, `NSWorkspace.OpenConfiguration.allowsRunningApplicationSubstitution = false`로 다른 설치본 재사용을 막았다. [Apple 문서](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/allowsrunningapplicationsubstitution)에 따르면 이 옵션의 기본값은 `true`다. 수정 빌드에서 사용자는 Esc 직후 재호출·호출 키로 닫기·설정 창 미표시를 확인했고, 로그는 정확한 시험 앱 1회 실행과 이후 재사용을 기록했다.

이후 제품 호출 모드와 시험 Helper의 `G1_PROBE` 환경 변수를 분리했다. 이 마지막 명칭·초기화 경로 변경은 빌드·앱 테스트를 통과했지만 물리 키로 다시 확인하지는 않았다. 수동 확인을 반복하기보다 격리 자동 검증을 우선 보강한다.

격리 설정 통합 시험에서는 출시 앱의 설정과 로그인 항목을 건드리지 않도록 별도 preferences suite, Caps Lock·메뉴·로그인 stub, 실제 `InputFeaturesAdapter`·`HelperClipboardCaptureHost`를 조합했다. 첫 활성화 취소는 기능을 켜지 않았고, 저장한 `⌥C`는 Helper 적용 성공 뒤에도 유지됐다. 처음에는 한글 입력 상태의 키를 `⌥ㅊ`로 보여주고 적용 후 `⌥#8`로 바꾸는 결함이 드러났다. ANSI 물리 키의 표시 이름과 적용·복구 시 표시값 보존을 수정한 뒤, CUA가 `⌥C`를 보여주고 격리 설정·적용 결과 모두 `displayKey=C`를 기록하는 것을 확인했다. 서식 포함 기본값 변경과 기능 끄기·재활성화도 적용 결과 `applied`로 확인했다. 이 시험은 UI에서 전역 키를 눌러 실제 히스토리 창을 다시 연 증거는 아니다.

사용자 요청으로 히스토리가 꺼져 있을 때 단축키·기본 붙여넣기·기록 삭제 행을 접었다. 한국어 밝은 모드 스냅샷에서 꺼진 카드가 줄어들고 켠 카드에 하위 설정이 보인다. 격리 설정 앱의 접근성 화면에서도 꺼짐에는 스위치만, `⌥C` 저장 후에는 하위 항목, 다시 끈 뒤에는 스위치만 남는 것을 확인했다. 현재는 전체 삭제도 꺼진 동안 숨겨지므로, 기능 끄기와 기존 기록 보존·삭제 정책 결정 때 함께 검토해야 한다.

격리 Helper에 읽기 거부 상태를 주입한 설정 UI 시험에서는 `⌥C`를 기록해도 적용 결과가 `failed / clipboardHistory.readDenied / enabled=false`였고, 스위치와 하위 설정이 꺼짐 상태로 돌아갔다. UI에는 클립보드 읽기 거부 안내가 표시됐다. 이는 제품 UI의 실패 처리 시험이며 실제 macOS TCC 거부·복구를 대신하지 않는다.

같은 격리 설정 흐름에서 `⌥C`를 `⌥B`로 변경하자 버튼, 임시 설정, Helper의 `applied` 결과가 모두 키코드 11·표시값 B로 갱신됐다. 기존 키의 물리 입력이 더 이상 호출되지 않는지는 직접 확인하지 않았으므로 AC-15 전체 통과로 표시하지 않는다.

세 화면 환경에서 기존 `panel.center()`만으로는 원래 앱의 화면을 지정하지 못한다. Helper가 원래 앱의 AX 활성 창 중앙이 속한 디스플레이 ID를 전달하고, 앱이 해당 화면의 보이는 영역 가운데에 창을 배치하도록 연결했다. AX 창을 읽을 수 없으면 마우스가 있는 화면을 사용한다. 현재 세 화면의 AppKit 좌표와 CoreGraphics 디스플레이 ID 대응은 읽기 전용 검사로 확인했지만, 각 화면·전체 화면에서 실제 호출 위치는 아직 확인 전이다.

재현 가능한 [격리 시험 스크립트](../Scripts/test-clipboard-history-gates.sh)의 일반 실행에서 ad hoc 빌드·물리 키·창·TextEdit 삽입·자동 정리까지 확인했다. 시험 Helper와 디렉터리는 종료 후 정리됐다.

세 실행 상태, 다중 모니터·전체 화면을 확인하기 전에는 G1 전체를 통과로 표시하지 않는다. G2의 다른 앱·서식·이미지와 G3 권한 거부·복구도 별도 확인이 필요하다.
