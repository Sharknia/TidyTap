# 클립보드 히스토리 기술 타당성 검토

- 작성일: 2026-09-23
- 상태: 사전 검토. 제품 기능의 구현·실사용 검증 완료를 뜻하지 않는다.
- 후속 결정: 2026-09-23에 보관 기간·용량·기능 끄기 동작(DEC-02·03)을 확정했다. 아래의 정책 미확정 평가는 사전 검토 당시의 기록이며 현재 결정은 [URS 7절](CLIPBOARD_HISTORY_URS.md)을 따른다.
- 요구사항: [클립보드 히스토리 URS](CLIPBOARD_HISTORY_URS.md)
- 검토 환경: macOS 26.5.2, Xcode 26.6, macOS SDK 26.5, 제품 최소 대상 macOS 15.1

## 결론

**조건부 구현 가능.** 현재 코드의 백그라운드 Helper, AppKit 앱, 설정 적용 경로와 macOS 기본 API로 기능을 구성할 수 있다. 로컬에서 데모 키의 등록·해제와 텍스트·RTF·PNG의 클립보드 표현을 확인했다. 이 확인은 사용자가 다른 앱에서 작업하는 전체 흐름의 성공을 증명하지 않는다.

전체 기능의 구현 경로와 완료 판단을 확정하기 전에 아래 두 조건을 작은 제품 내 실험으로 통과해야 한다. 작업 계획서에는 이 실험을 첫 단계로 넣을 수 있다.

1. 설정 앱을 `⌘Q`로 종료한 뒤에도 Helper의 호출 키가 **검색 가능한 창**을 띄우고, `Esc`·단축키 재입력으로 닫히며, `Enter`로 원래 입력 위치에 정확히 한 번 붙여넣을 것.
2. 지원 OS에서 백그라운드 클립보드 읽기의 허용·거부 동작이 확인되고, 거부 시 반복 알림 없이 중단·안내할 수 있을 것.

복사할 때마다 TidyTap이 해당 내용을 **별도로 저장하는 것**이 이 기능의 정상적인 설계다. macOS의 일반 클립보드는 과거 복사 목록을 제공하지 않는다. 빠른 연속 복사까지 **모든 중간 항목을 빠짐없이 저장한다는 보장**은 현재 API 조사와 실험으로 성립하지 않는다. 이 보장이 제품 요구라면 감시 방식을 추가 검증하고 URS의 완료 기준을 다시 정해야 한다. 일반 사용의 ‘복사 후 히스토리 확인’은 기술적으로 시도할 수 있으나, 아직 실사용 성공을 검증하지 않았다.

## 1. 현재 제품 구조에서 확인한 사실

| 확인 항목 | 현행 코드와 의미 |
| --- | --- |
| 장기 실행 | `Sources/Helper/main.swift`, `Sources/Helper/HelperRuntime.swift`가 설정 앱과 별도의 Helper를 실행한다. `TidyTapSettings.requiresHelper`가 켜진 기능이 없으면 Helper를 종료한다. 신규 토글도 수명 조건에 포함해야 한다. |
| 설정 적용 | `SettingsCoordinator`가 설정 스냅샷과 요청 ID를 저장하고 Helper가 읽어 적용 결과를 돌려준다. 단축키 등록 실패 시 토글을 켜진 것으로 남기지 않는 경로에 신규 상태를 연결해야 한다. |
| 전역 키 처리 | `CGEventTapBackend`의 키 이벤트는 현재 Finder 잘라내기가 켜진 경우에만 감시한다. 클립보드 호출 키가 이것에 의존해서는 안 된다. |
| 보조 창 | `FinderFeedbackAppHost`는 설정 앱이 없으면 앱을 비활성 상태로 시작할 수 있다. 현재 `FinderFeedbackPanelController`는 마우스 입력을 무시하는 1초짜리 알림이다. 검색·선택 창으로 그대로 사용할 수 없다. |
| 파일 붙여넣기 | `FinderCutPasteController`는 클립보드 변경 번호로 이동 대기를 관리한다. 히스토리 취소는 클립보드를 바꾸지 않아야 하고, 히스토리 붙여넣기로 클립보드를 바꾸면 과거 이동 대기가 되살아나지 않는지 검증해야 한다. |
| 대상 OS | 프로젝트의 최소 대상은 macOS 15.1이다. 새 OS 전용 클립보드 API는 가용성 분기를 거쳐야 하며, 최소 대상 OS에서 별도 실험이 필요하다. |

현행 구조가 확장 가능하다는 판단과 새 기능이 곧바로 동작한다는 판단은 다르다. 특히 기존 알림 창은 키보드 초점을 받는 인터랙티브 창이 아니다.

## 2. 로컬에서 수행한 비파괴 실험

실험 코드는 `/tmp/tidytap-*-feasibility.swift`와 임시 앱 번들에 작성했다. 저장소 코드·설정·시스템 클립보드 내용은 변경하지 않았다. 클립보드 데이터 실험은 고유 이름의 임시 pasteboard만 사용했다.

| 실험 | 관찰 결과 | 입증하지 못한 것 |
| --- | --- | --- |
| Helper에서 사용할 수 있는 Carbon 전역 단축키 API에 `⌃⌥⌘V` 등록·해제 | 이 Mac에서 등록 반환값 0, 핸들 생성, 해제 반환값 0 | 다른 앱과의 충돌 없음, Helper에서 실제 키 입력 수신, 설정 앱 종료·재시작 시 지속성 |
| macOS 15.1 대상 Swift 코드에서 `NSPasteboard.changeCount` 및 가용성 검사로 보호한 `accessBehavior` 타입 검사 | 현재 SDK에서 컴파일 성공 | 15.1 실기기 동작, 사용자별 클립보드 읽기 허용 상태 |
| 임시 pasteboard의 텍스트와 RTF를 한 항목에 기록·읽기 | 내용과 항목 수 1 확인 | 실제 앱에서 복사한 서식의 보존·대상 앱 렌더링 |
| 임시 pasteboard의 PNG 기록·읽기 | 내용과 항목 수 1 확인 | 스크린샷·브라우저 이미지 원본 수집, 외부 앱 이미지 붙여넣기 |
| 임시 pasteboard에서 A를 기록한 뒤 B로 교체 | 현재 내용은 B, 변경 번호는 1에서 2로 증가, 이전 A의 pasteboard item 읽기는 `nil` | 다른 앱의 실제 복사 간격이나 TidyTap의 감시 정확도 |
| 별도 Swift 실행 파일과 임시 `.app` 번들에서 인터랙티브 패널을 짧게 띄움 | 셸에서 실행한 직후에는 `canBecomeKey`만 참이고 `NSApp.isActive`·`isKeyWindow`·검색 필드 첫 응답자는 거짓이었다. 데스크톱 UI에서 임시 앱 창을 선택하자 검색 필드가 초점을 받았고 시험 문구 `probe`를 입력할 수 있었다. | Helper가 비활성 상태로 앱을 시작한 다음 사용자 클릭 없이 검색 필드에 초점을 주는 것, 실제 TidyTap 앱의 대상 복귀·붙여넣기. |

마지막 실험은 인터랙티브 검색 필드 자체가 가능함을 보여준다. 동시에 셸 시작과 데스크톱 앱 선택 사이에 초점 결과가 달랐다. 현재 설정 앱/Helper의 통신 경로와 서명·설치 조건은 재현하지 않았으므로, 호출 직후 **클릭 없이** 검색할 수 있는지는 실제 제품 경로의 소규모 실험으로 확인해야 한다.

### 클립보드 감시의 정확도 한계

macOS 일반 클립보드는 현재 복사 내용을 제공한다. 한 번의 복사에 여러 항목이나 텍스트·서식 같은 여러 표현이 들어갈 수 있지만, 이것이 **시간 순서의 복사 히스토리**라는 뜻은 아니다. TidyTap이 과거 항목을 다시 보여주려면 복사 당시 읽은 내용을 별도로 보관해야 한다. 임시 pasteboard에서 A를 B로 교체하자 현재 내용은 B였고, 붙잡아 둔 A 항목도 무효화됐다. [Apple `NSPasteboard` 문서](https://developer.apple.com/documentation/appkit/nspasteboard/), [Apple `NSPasteboardItem` 문서](https://developer.apple.com/documentation/appkit/nspasteboarditem)

따라서 ‘A가 날아간다’는 표현은 **TidyTap이 A를 저장하기 전에 B가 현재 내용을 대체했을 경우에만** 적용된다. 이미 TidyTap이 A를 저장했다면 B를 복사해도 A는 히스토리에 남는다. `changeCount`는 소유권 변경을 알려주는 값이지 지나간 버전의 내용을 돌려주지는 않는다. A·B가 감시 간격 안에서 연속 복사되고 현재 내용이 B라면, 변경 횟수를 알아도 A의 내용은 복원할 수 없다. 복사 키 이벤트만 관찰하면 메뉴·우클릭 복사를 놓친다. TidyTap은 변경을 감지할 때마다 가능한 빨리 내용을 저장하도록 만들고, 안전한 샘플 텍스트로 실제 놓침 정도를 계측해야 한다. [Apple `changeCount` 문서](https://developer.apple.com/documentation/appkit/nspasteboard/changecount)

### 클립보드 읽기 권한의 구분

현재 TidyTap의 손쉬운 사용/이벤트 수신 확인은 키 처리에 관한 것이다. 클립보드 내용 읽기 허용과 동일한 상태로 표시해서는 안 된다. Apple의 AppKit 업데이트는 향후 프로그램의 일반 pasteboard 읽기에 경고가 나타날 수 있고, 읽지 않고 종류를 확인하는 `detect`와 `accessBehavior`가 제공된다고 설명한다. 현재 macOS 26.5.2에서 해당 동작이 항상 활성화됐다는 주장은 하지 않는다. 지원 OS·실제 서명 앱에서 허용/거부/권한 변경을 검증한다. [Apple AppKit 업데이트](https://developer.apple.com/documentation/updates/appkit)

## 4. 본 구현 전의 검증 관문

| 관문 | 최소 실험 | 통과 기준 | 실패 시 결정 |
| --- | --- | --- | --- |
| G1. 창과 초점 | 실제 TidyTap 앱/Helper의 작은 실험 빌드에서 더미 텍스트 목록 한 항목과 검색 필드만 사용. 설정 앱 실행·종료·로그인 Helper 시작의 세 경로에서 호출 | 각 경로에서 호출 키로 창이 열리고 검색 필드가 입력을 받는다. 재호출·Esc로 닫히며 다른 설정 창이 뜻밖에 열리지 않는다. | 창 호스트·활성화 경로부터 재설계. 이 조건 없이 저장·검색 UI 전체 구현에 착수하지 않음. |
| G2. 대상 복귀 | 개인 데이터 대신 일회용 문구를 TextEdit, 브라우저 입력창, Terminal의 안전한 입력 상태에서 붙여넣기 | `Enter`/두 번 클릭마다 선택 문구가 원래 입력 위치에 한 번만 들어간다. 대상에 추가 Enter가 전달되지 않는다. 다른 앱으로 이동했거나 대상이 사라졌으면 잘못 붙이지 않는다. | 초점 복귀·이벤트 전달 순서를 수정. 모든 앱에서 된다는 약속을 하지 않음. |
| G3. 감시·권한 | 샘플 텍스트·이미지·Finder 이미지 파일을 복사하고 새 OS 클립보드 읽기 미리보기 및 설치 앱의 실제 권한 상태를 확인 | 지원 항목을 수집하고 파일을 제외한다. 거부 시 내용을 읽지 않고 반복 안내가 없다. 연속 복사 손실과 감시 비용을 측정한다. | 권한 안내 및 수집 계약을 수정. 백그라운드 감시가 허용되지 않으면 기능 범위 자체를 재검토. |

각 관문은 테스트 전용 데이터와 격리 설정으로 수행한다. 실제 사용자의 기존 클립보드·앱 권한·설치된 TidyTap 설정을 시험 데이터로 쓰지 않는다. 현재까지 G1~G3를 통과했다고 기록할 수 없다.

## 5. 계획서에 넘길 경계

작업 계획은 지금 세울 수 있지만 G1~G3의 성공을 전제로 전체 구현이 이미 검증됐다고 표시하지 않는다. 이 사전 검토 뒤 보관 기간·용량·끄기 동작은 확정됐다. 삭제 범위·동일 내용 중복 처리·서식 전환 키·민감 항목·안내 문구와 성능 기준은 아직 결정하거나 검증해야 한다.

구현 접근의 출발점은 **기존 Helper가 호출·감시를 맡고, 기존 앱 프로세스가 인터랙티브 창을 맡는 구조**다. Finder 알림용 시작·준비 신호는 참고하되, 복사 본문을 분산 알림에 싣거나 또 다른 상주 앱/시스템 확장을 추가하지 않는다. 이 접근은 G1·G2 통과를 전제로 한 후보이며 최종 설계 결정은 아니다.
