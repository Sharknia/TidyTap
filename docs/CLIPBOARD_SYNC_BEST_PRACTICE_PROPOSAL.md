# 클립보드 iCloud 동기화: 아스트라 협의와 권고

- 작성일: 2026-11-13
- 상태: 협의 당시 기술 제안 기록. 이후 사용자가 관리형 우선 검증과 OFF=일시중지/ON=기록 병합을 채택했다. 최신 실행 기준은 [작업 계획](CLIPBOARD_PINBOARD_ICLOUD_PLAN.md)이며 구현·두 Mac 수용·배포 완료는 아니다.
- 범위: 최근 텍스트/이미지 기록·고정 보관함 1개·같은 Apple 계정의 Mac 간 동기화·기기별 on/off·삭제/오프라인 복구.
- 방법: 아스트라(gpt-6-astra, high)를 부모 대화 없는 새 문맥에서 실행했다. 첫 프롬프트에는 요구만 주고 기존 계획·이전 권고를 주지 않았다. 이후 Apple 근거·실제 코드의 정책·반례를 대조했다. [첫 프롬프트](research/clipboard-sync-2026-11-13/ideation_prompt.md), [협의 기록](research/clipboard-sync-2026-11-13/consultation_summary.md).

## 1. 권고

**Core Data의 로컬 저장과 `NSPersistentCloudKitContainer`의 개인 CloudKit 미러링을 먼저 두 Mac에서 검증한다.** 삭제 이력·전송 재시도·복구 수신증을 직접 설계하기 전에 Apple이 저장과 변경 이력을 함께 관리하는 방식을 시험한다. 통과 시 채택하고, 실제로 맞지 않는 조건이 확인되면 그 조건을 근거로 기존 저장+CKSyncEngine을 다시 비교한다.

이 권고는 기존 파일 이관 비용만 보고 판단한 앞선 CKSyncEngine 우선안에서 변경됐다. 파일 저장을 유지해도 새 항목 식별·고정 상태·변경 대기열·삭제/전송 복구·계정 구분이 필요하다. 기존 파일 재사용이 전체 개발/유지 비용의 최소를 뜻하지는 않는다. 두 구현의 실제 작업량·성능을 측정한 것은 아니며, 현재 코드와 공개 API의 책임 경계를 비교한 기술 판단이다.

Apple은 Core Data 미러링이 로컬 저장 시 persistent history에 변경을 기록하고 원격으로 export/import한다고 설명한다. 직접 로컬 저장을 유지하려면 CKSyncEngine을 쓸 수 있지만 앱별 충돌·로컬 상태 처리도 앱이 맡는다. [Core Data 동작](https://developer.apple.com/documentation/technotes/tn3163-understanding-the-synchronization-of-nspersistentcloudkitcontainer), [Apple API 선택 설명](https://developer.apple.com/videos/play/wwdc2023/10188/?time=97).

## 2. 삭제 기록은 어디까지 필요한가

현재 앱의 개별·전체 삭제는 로컬 파일을 제거하는 기능이다. 동기화를 도입하면 ‘여기에 항목이 없음’만으로는 삭제·미수신·로컬 정리를 구분할 수 없다. **변경/삭제를 전달할 내부 상태는 필요하다.** 그것이 사용자에게 보이는 휴지통·삭제 목록이나 삭제한 본문 전체의 영구 이력일 필요는 없다.

권고는 앱에서 영구 삭제 감사 로그를 새로 만드는 대신 관리형 변경 이력과 개인 DB의 삭제 전달 경로를 쓰는 것이다. Apple은 private DB와 public DB의 삭제 전달 차이도 설명한다. 공개 DB에 필요한 soft-delete 예제를 이 앱의 개인 DB에 그대로 적용하지 않는다. [개인/공개 DB 설명](https://developer.apple.com/videos/play/wwdc2020/10650/?time=475), [기술 노트의 공개 DB 삭제 제한](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer).

이력 정리도 본문의 7일 만료와 별개다. CloudKit export와 앱/Helper 등 소비자가 아직 필요한 persistent history를 단순히 ‘7일 지났다’며 지우지 않는다. 소비한 이력·완료된 export·안전한 정리 범위를 확인해야 한다. 본문·인증정보를 앱의 별도 삭제 로그에 남기지 않는다. [Apple persistent history 정리 조건](https://developer.apple.com/documentation/coredata/sharing-core-data-objects-between-icloud-users), [이력 소비와 삭제 값 보존](https://developer.apple.com/documentation/coredata/consuming-relevant-store-changes).

## 3. ‘SDK 기본 삭제면 충분’이라고 단정할 수 없는 이유

Apple의 CKSyncEngine 연락처 샘플은 서버에서 레코드를 찾을 수 없는 `unknownItem`에 대해 같은 ID를 다시 업로드하는 정책을 의도적으로 선택한다. 샘플의 정상 동작이 클립보드에서 원하는 삭제 우선 정책과 같지는 않다. [샘플 오류 처리](https://github.com/apple/sample-cloudkit-sync-engine/blob/main/SyncEngine/SyncedDatabase.swift), [해당 재업로드 시험](https://github.com/apple/sample-cloudkit-sync-engine/blob/main/Tests/SyncTests.swift).

특히 다음 두 상황은 첫 전송 승인을 기록하지 못한 클라이언트에 비슷하게 보일 수 있다.

1. 처음부터 서버에 도달하지 못한 생성 요청.
2. 서버에는 생성됐지만 로컬이 승인을 기록하기 전에 종료되고, 다른 Mac이 삭제한 항목.

서버에 지금 항목이 없다는 조회만으로 둘을 구분해 자동 재생성하면 안 된다. 이것은 삭제 이벤트 전달 API의 존재와 다른 문제다. 아스트라는 결과 불명 항목의 새 배치 공급을 중단하는 안을 제안했지만, 내부 네트워크 재시도까지 매번 그 검사를 거친다는 공개 보장을 확인하지 못해 ‘부활 방지 보장’을 철회했다. 주 에이전트도 현재 설치 SDK의 CKSyncEngine/Configuration/RecordZoneChangeBatch 헤더와 공개 문서에서 그 보장을 확인하지 못했다. 실제로 항상 문제가 발생한다는 뜻은 아니다. [엔진 배치/재시도 계약](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5).

따라서 앞선 ‘기본 삭제 전파만 넣고 오래된 재전송 문제는 뒤로 미루자’는 권고는 다음처럼 보완한다. 일반적인 삭제 전달은 기본 기능에 넣되, **삭제한 내용의 뜻하지 않은 재생성은 필수 시험 대상**으로 둔다. 모든 오류 상황에 대한 영구 무결성 보장을 선언하거나 직접 새 분산 프로토콜부터 만드는 것은 권하지 않는다.

## 4. 비교한 구현 방식

| 선택지 | 이점 | 이 앱에서 부담할 비용·한계 | 판단 |
| --- | --- | --- | --- |
| Core Data + NSPersistentCloudKitContainer | 로컬 저장과 변경 이력·미러링을 같은 프레임워크가 관리. 파일 저장과 별도 전송 상태의 원자성 문제를 앱이 전부 직접 맡지 않음 | 파일/이미지 이관, 모델 제약, 앱/Helper 처리, OFF 의미, 중복·수명 정책은 필요. 모든 충돌의 자동 해결을 보장하는 API가 아님 | **우선 검증 권고** |
| 현재 파일 + CKSyncEngine | 기존 파일·직접 CKRecord/CKAsset 제어와 수동 fetch/send 사용 가능 | 데이터·pending 변경·엔진 state·서버 버전·이미지 수명·생성/삭제 경합을 직접 관리. 공개 계약에 없는 재시도 순서를 전제로 안전하다고 주장할 수 없음 | 관리형 방식의 구체적 부적합이 확인되면 대안 |
| 직접 생성 수신증/설치별 순번 프로토콜 | 원자적 수신증이 정확히 설계되면 ACK 불명의 증거를 추가할 수 있음 | 연속 순번·CAS·원자 배치·중간 실패·복원/설치 ID·정리·선두 실패의 전송 차단까지 별도 검증. CK 배치의 atomicByZone 기본값도 false | 첫 버전에서 채택하지 않음 |
| 항목마다 영구 삭제 표식 | 같은 ID의 늦은 생성/수정을 거절할 근거가 남음 | 만료까지 모두 기록하면 레코드 누적. 안전한 GC 조건 없이 TTL만 붙이면 문제가 다시 생김 | 일반 해법으로 권하지 않음 |

이 앱은 개인 DB를 사용하므로 iCloud Drive의 단일 JSON 파일 병합이나 1MB 키-값 저장소를 주 저장소 대안으로 우선하지 않는다. 모델 변경·이미지·삭제를 다루기 위해 플랫폼의 데이터 동기화 계층을 선택한다.

**표식 비용의 예시:** 하루 1,000개 만료에 각각 영구 표식을 만들면 365일에 365,000개가 추가된다. 사용자의 실제 사용량 추정이나 저장 용량 측정은 아니다. CloudKit 메타데이터를 포함한 바이트 크기는 측정하지 않았으므로 작다고 단정하지 않는다. 순번 대안 역시 API의 원자 배치를 켜는 것만으로 정확한 프로토콜이 되는 것은 아니다. [Apple 원자 배치 옵션](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5/recordzonechangebatch/atomicbyzone).

## 5. 관리형 방식에서도 앱이 정해야 하는 동작

| 항목 | 권고하는 경계 |
| --- | --- |
| 동기화 주기 | 시스템 자동 일정 사용. ‘매 N초’나 항상 최신을 보장하지 않음. Core Data의 일반 fetch는 로컬 store 조회이므로 네트워크 강제 새로고침이라고 표시하지 않음 |
| 기록 ID | 사용자 동작으로 생성한 논리 항목에 안정된 식별자를 유지. 원격 import·재전송 때문에 새 ID를 만들지 않음. 삭제 ID를 같은 본문의 새 복사에 무조건 재사용하지 않음 |
| 중복 표시 | 현재 본문+서식 동일 항목의 최신 1건 표시를 유지. 동시 import의 중복·고정·사용 시각을 함께 시험. 단순한 CloudKit 유일성 제약으로 해결한다고 가정하지 않음 |
| 고정/만료 | 고정 보관과 최근 기록의 수명을 분리. 일반 기록의 만료/용량 정리로 확인된 고정 본문을 없애지 않음. 오프라인 고정과 이미 확정된 삭제의 충돌 정책은 사례별로 명세하고 실제 결과 확인 |
| 최근 사용 | 현 코드는 붙여넣기 시도 시작 시각을 갱신하며 실패도 되돌리지 않는다. 이 동작과 그 시각 기준 7일을 유지. 원격 수신만으로 만료 시점을 연장하지 않음 |
| 만료/용량 정리 | 명시적 삭제와 로컬 공간 확보를 구분. mirrored 객체를 지우면 공유 삭제가 될 수 있으므로 기기별 캐시 퇴출에 그대로 쓰지 않음. 공유 보관 한도와 로컬 점유 한도의 의미는 채택 전에 결정 |
| 일반 기록 삭제 | 고정 보관함 보존 여부와 일치하도록 모델·버튼·동작을 연결. Core Data가 이 제품 정책을 대신 정한다고 주장하지 않음 |
| 전체 삭제 | 가장 작은 기준안은 현재 알고 있는 대상 ID 삭제. 미수신·오프라인 미래 복사까지 지운다는 약속을 하지 않음. 모든 Mac 전체 초기화가 필요하면 별도 요구로 정의 |
| 계정 | Apple 계정별 store/상태 분리와 이전 outbox 자동 반입 금지. 계정 변경을 다른 계정으로 데이터 옮기기나 원격 전체 삭제로 해석하지 않음 |
| 앱/Helper | 미러링 소유 프로세스 하나. Helper가 UI 종료 중 수집한 변경도 이후 export. 여러 프로세스가 같은 store를 쓰면 context author·소비자별 history token·원격 변경 알림/재조회 계약 필요 |

Core Data CloudKit 모델은 유일성 제약 등을 지원하지 않는다. 따라서 기존 중복 정책과 임의의 관계 삭제 규칙을 프레임워크 기본값으로 갈음할 수 없다. [Apple 모델 제약](https://developer.apple.com/documentation/coredata/creating-a-core-data-model-for-cloudkit). 자동 일정의 제한과 로컬 fetch 의미는 [동기화 기술 노트](https://developer.apple.com/documentation/technotes/tn3163-understanding-the-synchronization-of-nspersistentcloudkitcontainer)와 [시간 제어 제한](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer)에 근거한다. 다중 프로세스 소비는 [Core Data 변경 이력 설명](https://developer.apple.com/videos/play/wwdc2020/10017/?time=390)을 참고한다.

## 6. OFF는 제품 정책을 분명히 해야 한다

네트워크 끄기와 OFF 동안 만든 내용을 나중에도 비공개로 유지하기는 다르다. 후속 사용자 결정은 OFF=일시중지, ON=유효한 로컬/원격 기록 병합이다. 아래 비교는 결정 이전 대안 검토 기록이다.

| 의미 | 이점·비용 | 제안 |
| --- | --- | --- |
| 동기화 일시중지 | OFF 동안 송수신 중단, ON 후 유효한 로컬 변경도 병합. 하나의 공유 데이터 집합과 잘 맞지만 OFF 중 복사도 나중에 올라갈 수 있음 | v1 범위를 작게 유지하는 안. 채택하면 ‘다시 켜면 보관 중인 기록도 동기화’라고 명확히 안내 |
| OFF 중 새 복사는 이 Mac 전용 | 재활성화가 과거의 비공개 복사를 몰래 업로드하지 않음. 처음부터 local-only store/참여 상태와 중복/고정 경계를 관리해야 함 | 클립보드의 비공개 의도를 우선하는 아스트라 초기 권고. 단순 export 중지로 구현하지 않음 |

기술 베스트 프랙티스는 의미를 숨기지 않고 선택한 정책과 저장 구성을 맞추는 것이다. 사용자는 이후 일시중지를 채택했고 새 복사의 영구 local-only 모드는 채택하지 않았다. 이미 공유된 항목의 OFF 중 고정·삭제와 진행 중 export 취소 결과도 따로 정의해야 한다. [Apple 복수 store/CloudKit 구성](https://developer.apple.com/documentation/coredata/setting-up-core-data-with-cloudkit).

## 7. 먼저 수행할 제한된 기술 실험과 판정

기존 라이브러리와 별도인 시험 계정·컨테이너/영역·합성 데이터로 두 Mac의 서명 후보를 검증한다. 자동 fixture 시험과 실제 프레임워크의 네트워크 재시도 관찰을 구분한다. 전체 구현/이관을 먼저 완료하고 뒤늦게 맞지 않는다고 판단하지 않는다.

| 시험 | 합격 조건 | 실패·관찰 한계 처리 |
| --- | --- | --- |
| 정상 생성/삭제 | 텍스트·서식·이미지 생성과 개별/전체 삭제가 상대에 반영. 선택한 고정 보존 정책과 일치 | 전달만 확인하고 오래된 전송 부활까지 통과라고 표시하지 않음 |

관리형 방식이 선택한 OFF·삭제·고정·용량 의미를 충족하지 못한다는 구체적인 결과가 있으면, 그 실패를 해결할 CKSyncEngine 직접 제어 설계를 비교한다. 직접 구현으로 돌아갈 때도 샘플의 `unknownItem` 재업로드·영구 표식·독자 수신증을 검토 없이 기본값으로 채택하지 않는다.

## 8. 현재 등급과 미확인 범위

- **중간·미확인:** 두 Mac 삭제/재시도·OFF·계정·한도·다중 프로세스 시험이 아직 없다. 현재 신규 동기화 기능 구현 전이며 실제 데이터 손상이나 배포 실패를 관찰한 것은 아니다.
- **해당없음:** 위 시험을 후보 채택의 필수 관문으로 삼는다. 아스트라가 일부를 ‘차단/높음’으로 표기한 것은 그 시험 없이 안전성을 선언하면 안 된다는 관문 관점이다. 현재 앱에 그 등급의 장애가 발생한 것으로 전달하지 않는다.
- **해당없음:** 후속 사용자 요청으로 기존 작업 계획을 관리형 후보 우선 검증과 일시중지 정책에 맞게 개정했다. 당시 제안을 바로 제품 구현으로 적용한 것은 아니다.

이번 작업은 독립 아이데이션·근거 대조·협의·제안까지다. 저장 모델 작성·계정/프로파일 변경·네트워크 오류 주입·이관·두 Mac 실제 시험은 수행하지 않았다. 최종 권고는 우선 검증할 경로이며 삭제 정합성을 실기기로 입증했다는 결과가 아니다.
